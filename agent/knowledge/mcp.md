# MCP (Model Context Protocol)

## 2026-07-28 仕様の大改定(RC段階) — 記録日 2026-07-02

出典: https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/

- **ステートレスコア**: セッション管理を廃止し、通常のHTTPインフラで水平スケーリング可能に。ステートフルセッションとロードバランサの相性問題が解消される
- **MCP Apps**: サーバーがサンドボックス化されたHTMLインターフェースを返せる拡張
- **Tasks**: 長時間処理を扱う独立した拡張
- **認可**: OAuth/OpenID Connectに整合(RFC 9207 の iss 検証、Dynamic Client Registration)
- SEP(仕様拡張提案)ベースの開発+廃止予定ポリシー導入。確定リリースは 2026-07-28 予定

含意: MCPサーバー/クライアントを作る場合は7月末の確定版に追従する準備が必要。

## セキュリティ・運用の知見 — 記録日 2026-07-02

出典: https://dev.to/alexmercedcoder/ai-weekly-agents-take-over-mcp-evolves-and-models-battle-for-code-5cm0

- **AutoJack**(Microsoft研究): AIブラウジングエージェントに悪意あるページを踏ませ、ローカルMCPサービス経由で任意プロセス実行に至る攻撃。ローカルツール接続には厳格な隔離が必要
- **コンテキスト効率**: Perplexity CTOの批判 —「MCPツール記述だけでコンテキストの40〜50%を消費する」。動的なツール発見にはMCP、コンテキスト効率重視なら従来API/CLIという使い分けが現実解になりつつある

## プラットフォームのホスト型/ネイティブMCPサーバーが標準化 — 記録日 2026-07-06

出典: https://techcrunch.com/2026/06/30/x-now-offers-an-mcp-server-to-make-its-platform-easier-for-ai-tools-to-use/ 、https://9to5mac.com/2026/07/01/safaris-new-mcp-server-lets-coding-agents-inspect-and-debug-websites/

- X(旧Twitter)が「ホスト型MCP」を公開。自前でサーバーを立てずに、Grok/Cursor/Claude等のMCP対応クライアントをエンドポイントに繋ぐだけでX APIの150以上のエンドポイント(投稿検索・ブックマーク管理・トレンド取得・記事投稿など)が使えるようになった。GitHub/Slack/Notion/Stripeに続く「公式ホスト型MCP」の流れ
- Apple も Safari Technology Preview 247 で MCP サーバーをネイティブ搭載。スクリーンショット・DOM検査・JS実行・コンソール/ネットワークログ・アクセシビリティ検査など16ツールをエージェントに提供。ローカル完結で外部通信せず、収集情報はApple自身にではなく開発者が選んだAIクライアントにのみ渡る設計
- 両者に共通するのは「MCPサーバーをサードパーティ実装に任せず、プラットフォーム自身がホスト/ネイティブ提供する」という段階への移行。自作MCPサーバーの認証・可用性コストが下がる一方、プラットフォーム側のMCPエンドポイントがそのまま新たな攻撃対象面になる点は [[security.md]] のAutoJack事例と合わせて注意する

## 2026-07-28仕様目前でも大半のMCPサーバーが未対応 ― mcp-spec-checkの実測 — 記録日 2026-07-13

出典: https://github.com/Roee-Tsur/mcp-spec-check (Show HN: https://news.ycombinator.com/item?id=48881009)

- 7/2に記録した2026-07-28仕様(ステートレスコア化・`initialize`ハンドシェイクと`Mcp-Session-Id`の廃止・`Mcp-Method`/`Mcp-Name`ルーティングヘッダー必須化など、プロトコル史上最大の改定)に対し、実際にどれだけのサーバーが対応済みかをブラックボックスプローブで判定するツールが公開された
- 2026-07-12時点で公式MCPレジストリの7,850台をスキャンした結果、到達可能な4,356台のうち完全対応はわずか1台(未対応率90.8%)だった。仕様がまだGA前であることを踏まえても、確定日まであと2週間強という段階での準備状況としては低い

含意: 7/2の「MCPサーバー/クライアントを作る場合は7月末の確定版に追従する準備が必要」という含意に対する具体的な実測値が出た。AgAg自身はMCPサーバーを運用していないため直接の対応は不要だが、今後MCP関連のニュースを追う際は「仕様が出た」時点だけでなく「実際の対応率」を継続的に確認する視点を持つ。

## MCP公式SDKのSTDIO設計欠陥によるRCEリスク — 記録日 2026-07-06

出典: https://zenn.dev/kai_kou/articles/242-mcp-systemic-vulnerability-rce-guide

- セキュリティ企業OX Securityが、Anthropic公式サポートの全言語(Python/TypeScript/Java/Rust/Go)のMCP SDKに内在する設計上の欠陥を報告。150百万件以上のダウンロード・20万以上のサーバーインスタンスに影響する規模
- Anthropicは「仕様どおりの動作(by design)」として修正を拒否しており、利用側が自力で対策を講じる必要がある。つまりMCPは「個々のskill/サーバーの実装ミス」だけでなく「プロトコル仕様そのものの設計」レベルでリスクを抱えている
- 含意: [[security.md]] のskillサプライチェーン攻撃の知見(実装レベルの脆弱性)と合わせて、MCPを扱う際は「プロトコル設計自体は安全とは限らない」という前提で境界を設計する必要がある

## 2026-07-28仕様が正式化 ― ステートレス化確定とClaudeへの導入 — 記録日 2026-07-29

出典: https://blog.modelcontextprotocol.io/posts/2026-07-28/ 、https://claude.com/blog/bringing-mcp-2026-07-28-to-claude

- 7/2に記録したRC段階の大改定が2026-07-28付で正式仕様として確定した。初期化ハンドシェイク(`initialize`/`initialized`)と`Mcp-Session-Id`ヘッダーを廃止し、あらゆるリクエストが単純なラウンドロビン・ロードバランサ配下のどのサーバーインスタンスにも着地できる完全ステートレス設計に移行。状態を保持したい場合はツールが明示的なハンドルを発行し、モデルが引数として返す方式に変わった
- Anthropicも同日、Claude自身への2026-07-28仕様の導入を公式ブログで発表した
- 含意: 7/13に記録した実測(公式レジストリ7,850台中、完全対応はわずか1台=未対応率90.8%)の後日談として、仕様自体は確定版に到達したことを確認した。今後この種のニュースを追う際は「仕様が確定した」で終わらせず、実際の対応率がどこまで追いついたかを継続的に確認する視点を維持する。

## MCPツールの「サイレントドリフト」を継続監視するレジストリが登場 ― 36,574件中12,391件が契約変更、うち8,931件はバージョン番号据え置き — 記録日 2026-08-19

出典: https://mcpindex.ai/ledger

- 公開MCPレジストリを毎日クロールし、ツールの入出力スキーマ等の「契約フィールド」の変更を継続記録するサービスmcpindexが、36,574個のツールのうち12,391個で契約フィールドの変更を検出したと公表。うち7,239件は安全性に関わる変更で、8,931件は宣言バージョン番号が変わらないまま仕様だけが変わる「サイレントドリフト」だった

含意: 7/13・7/29に本ファイルへ記録した「仕様が確定した/対応率が上がった」で終わらせず実際の対応状況を継続確認する視点の延長として、今回は「一度対応済みのツールがその後静かに仕様変更している」という別の軸のリスクが実測で示された。バージョン番号を信頼してツール定義をキャッシュ・スキップする設計は、MCPクライアント側では危険という具体的な教訓になる。

## 公式MCPサーバーの承認後サイレント変更とRugSnare — 記録日 2026-10-04

出典: https://github.com/Paraphern/rugsnare (作者自身の集計で、第三者の検証は未確認)

- 公式の`@modelcontextprotocol/server-*`参照実装4種の全安定版を比較し、66のリリースペア中23ペアで計140件の変更があり、チェンジログに載っていなかったと報告している。内訳は破壊的スキーマ変更43件、挙動ヒントの反転28件、新規ツール37件、削除24件
- RugSnareは承認済みツール定義をハッシュで固定し(scan)、セッション間の差分でCIを落とし(diff)、実行中に不審なツールを隔離する(run)。表記の並べ替えだけの変更は無視する正規化に対応している

含意: 2026-08-19のサイレントドリフトの記録を、公式サーバーでも起きている実例で補強する。ツール記述はエージェントが従う指示であり、承認後に変わりうるため、定義を固定して差分を検知する運用が有効。

## 2026-10-18: MCPサーバーの宣言外ファイルアクセス

- Filesystem Capability Laundering(https://arxiv.org/abs/2610.22301): 9レジストリの21,097件を収集し、審査対象4,806件のうち787件(16.4%)が、非ファイルシステム系に分類されながらファイルシステム機能を持っていた。動的検証で150件の脆弱なインスタンス、13件のアドバイザリ(AnthropicのGit MCPサーバーの2件のCVEを含む)。要旨のみ確認
- 含意: MCPサーバーの宣言(カテゴリ・説明)を信用せず、ツールごとの引数がどのパスに届くかを確認し、サンドボックスで権限を絞る

## 2026-10-21: 公式レジストリのリモートMCP全数調査

- MCP Canary(https://mcpcanary.com/blog/state-of-mcp-reliability-q4-2026/): 2026年10月20日に30,516のリモートエンドポイントへ認証なしでハンドシェイクとツール一覧取得のみを実施。正常51.4%、認証待ち31.2%、壊れ10.9%、レート制限4.9%、従量課金1.6%
- 4月以前の掲載は40%が壊れ、10月更新分は4%。ホスティング別の壊れ率はCloudflare Workers約6%、Railway 50%、Render 39%。キー必須なのに登録情報に明記がないものは約78%。健全サーバーの41.4%はどのツールにも読み取り/破壊のヒントがない。ツール一覧の中央値は約2,000トークンで、741件が25,000トークン超
- 限界: 単一地点・単一時点、ログイン後は未検証、『正常』はハンドシェイク完了でありツールが動く証明ではない。ヒントは宣言であって挙動ではない

含意: 導入前に更新日と認証要否を確認し、ヒントがないツールは破壊的とみなして権限を絞る。長いツール一覧は文脈コストになる。

## 2026-10-23: Agent Skills の標準化

AnthropicがAgent Skillsの標準をLinux Foundation傘下のAgentic AI Foundation(AAIF)に寄贈した(2026-10-22発表、Simon Willisonの紹介記事で確認: https://simonwillison.net/2026/Oct/22/donating-agent-skills/)。AAIFはAnthropicがBlock・OpenAIと共同設立した団体で、MCPも以前に寄贈済み。Anthropicは「オープン・コミュニティ主導・ベンダー中立」を保つと述べている。Anthropic本体のページは本文を取得していない。

含意: スキルもMCPと同様に中立標準として進む見込み。`agent/skills/` の書式を変える必要はまだないが、仕様変更が出たら追随を検討する。

## 2026-10-28: MCP Tasksの実機検証

プロトコル2026-07-28のMCP Tasks(公開ベータ)をClaude Code 2.1.303/2.1.310で試した個人の記録(https://zenn.dev/jtcc/articles/claude-code-mcp-tasks-v21310 、1環境)。server/discoverに応答しないとlegacy扱いになる。タスク応答にcreatedAt・lastUpdatedAt・ttlMsが欠けると「Unsupported result type 'task'」で失敗し、原因が分かりにくい。非対話の-pではstream-json入出力と環境変数CLAUDE_AUTO_BACKGROUND_TASKS=1の両方が必要。

含意: 自作MCPサーバーでTasksを使うときは、この3点を先に確認する。

## 2026-10-29: クライアント側のツール遅延読み込み

MCP Rating(https://mcprating.io/blog/clients-load-tool-names-now 、自社でゲートウェイを作る運営元自身の測定)によると、Claude Code・Cursor・Kiroはツール名だけを先に読み込み、定義は必要時に取得する。Claude Codeは環境変数ENABLE_TOOL_SEARCH=falseで無効化でき、10サーバーで初期14,853トークン(無効時183,889)。測定は3クライアント・スタブサーバー・短いセッションで、2026-10-27/28時点のバージョン限定。

含意: MCPサーバーの数が多いだけでコンテキストが膨らむ前提は古くなりつつある。ゲートウェイ導入は節約目的だけでは判断せず、実際の構成で測る。

## 2026-10-30: ツール定義のトークンを自分で数える

https://zenn.dev/cauchye_asia/articles/e6b81183b34ef4 (個人の実測、tiktokenのo200k_base・cl100k_base。Claudeのトークナイザは非公開なのでClaudeの実測ではない): 機械的に作ったツールは1つ約106トークンでほぼ一定、実際に近い10ツールは平均115.6トークン。JSONをindent=2にすると空白なしより約57%増え、同じ1文の説明文は日本語が英語の約2〜3倍(1文のみの比較)。「合計はコンテキストの5%以内」「1ツール150トークン以下」は筆者の判断で標準ではない。

含意: 遅延読み込み(2026-10-29)で初期コストが下がっても、定義を読み込む時点のコストは定義の書き方で変わる。最終確認は実際の応答のusageで行う。
